# Локальная AI-модель вместо внешнего провайдера

Версия: 25 сентября 2026 года.

Анализ использует AI ровно для трёх задач: описать область поиска по запросу,
назвать группу документов конкретным механизмом и выбрать цитаты для паспорта.
Всё, что решает, станет ли кандидат трендом, остаётся на прежних проверках
против архивных документов — модель только предлагает формулировку.

До этой работы три задачи выполнял только платный провайдер. Без ключа
именование не запускалось, и запасной лексический путь ставил каждому кандидату
`specificity = "uncertain"`. Отбор в ТОП-15 принимает только
`specific_technology` ([selection.py](../../app/pilot/selection.py)), поэтому без
ключа ТОП всегда оставался пустым, а все кандидаты уходили в очередь
непроверенных гипотез. Локальный провайдер закрывает именно этот разрыв.

## Что установлено

| | |
|---|---|
| Модель | `onnx-community/Qwen2.5-1.5B-Instruct`, ревизия `6287331f…9d34` |
| Файл весов | `onnx/model_q4.onnx`, 1,79 ГБ, 4-битные веса |
| Токенизатор | `tokenizer.json`, 7,0 МБ |
| Размерность | 28 слоёв, 12 голов внимания, 2 KV-головы, head_dim 128 |
| Куда ставится | `<каталог профиля>/models/qwen2.5-1.5b-instruct` |

Спецификация с точными размерами и SHA-256 закреплена в коде
([local-llm-spec.json](../../app/pilot/local-llm-spec.json)) и проверяется перед
каждым запуском, как у остальных моделей.

```sh
.venv/Scripts/python.exe -m scripts.install_local_llm
```

То же самое делает кнопка «Загрузить / проверить AI-модель» в настройках
анализа: она вызывает ровно эту установку и показывает полосу с уже полученными
мегабайтами, обновляя её каждые 0,3 с. Загрузка идёт в рабочем потоке, в
интерфейс переходят только два числа, поэтому окно остаётся отзывчивым; на время
загрузки анализ не запускается, а закрытие приложения её прерывает и не
оставляет недокачанный каталог. Новому разработчику терминал для этого больше не
нужен.

Команда и кнопка — единственное место, которое обращается к сети за этими
весами. Сам анализ не скачивает ничего. Веса загружаются отдельно и занимают около 1,8 ГБ.

## Как включить

В настройках анализа выбрать поставщика `local` и, если веса ещё не установлены,
нажать кнопку загрузки — строка рядом с ней прямо говорит, установлена модель или
нет (`status()` отвечает на это по размерам файлов, без чтения 1,8 ГБ; хеши
по-прежнему проверяются перед запуском). Ключ и интернет не нужны,
запросы бесплатны, лимиты вызовов и токенов остаются прежними — они ограничивают
уже не деньги, а время прогона.

## CUDA на отдельном сервере с RTX 3070 или 4070

Эти шаги относятся к запуску **из исходников** на Windows x64 или Linux x64 с
Python 3.13. Сначала подготовьте обычную `.venv` и зависимости проекта по
[README](../../README.md); затем замените только CPU-сборку ONNX Runtime на GPU-сборку.
Проект закрепляет ONNX Runtime 1.29.0: [официальная таблица совместимости](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)
указывает для неё CUDA 13.0 и cuDNN 9.x. Драйвер NVIDIA для CUDA 13 должен быть
не ниже ветки 580 по [таблице NVIDIA](https://docs.nvidia.com/cuda/archive/13.0.3/cuda-toolkit-release-notes/index.html#cuda-driver).
Проверьте фактическую видеокарту и драйвер на будущем сервере командой `nvidia-smi`.
Напечатанная там «CUDA Version» означает [максимальную версию CUDA, доступную
драйверу](https://docs.nvidia.com/datacenter/tesla/drivers/cuda-toolkit-driver-and-architecture-matrix.html),
а не установленную версию набора инструментов. Эти параметры сервера пока неизвестны.

После установки обычных зависимостей выполните **в каталоге проекта**:

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip uninstall -y onnxruntime onnxruntime-gpu
.\.venv\Scripts\python.exe -m pip install -r requirements/cuda.txt
.\.venv\Scripts\python.exe -m scripts.setup_models --web-analysis
.\.venv\Scripts\python.exe -m scripts.check_cuda_runtime
```

Linux:

```sh
.venv/bin/python -m pip uninstall -y onnxruntime onnxruntime-gpu
.venv/bin/python -m pip install -r requirements/cuda.txt
.venv/bin/python -m scripts.setup_models --web-analysis
.venv/bin/python -m scripts.check_cuda_runtime
```

Оба дистрибутива ONNX Runtime предоставляют модуль `onnxruntime`; держать их
одновременно в одном окружении нельзя. Файл `requirements/cuda.txt` устанавливает
закреплённую GPU-сборку вместе с библиотеками CUDA и cuDNN через официальные
дополнения пакета. cuBLAS 13 указан отдельно, поскольку в дополнительных
зависимостях ONNX Runtime 1.29 он не перечислен напрямую. Устанавливайте
GPU-сборку **после** `requirements/semantic.lock`:
повторная установка обычных зависимостей может вернуть CPU-сборку. На Windows
также нужен [Microsoft Visual C++ 2019 Runtime](https://onnxruntime.ai/docs/install/#requirements),
на Linux — системная `zlib` для cuDNN 9.

`setup_models --web-analysis` готовит закреплённые веса Qwen и многоязычной E5
для научного анализа, а также модель перевода. `check_cuda_runtime` проверяет
GPU-пакет и короткое вычисление **обеих** моделей через `CUDAExecutionProvider`.
Для проверки нужны установленные веса; она не скачивает их сама. Если проверка не прошла,
не начинайте длительный анализ в ожидании ускорения: ONNX Runtime может
незаметно перейти на CPU. Принудительный режим для запуска анализа:

```powershell
$env:TRENDANALIZER_INFERENCE_PROVIDER = "cuda"  # PowerShell
```

```sh
export TRENDANALIZER_INFERENCE_PROVIDER=cuda  # Linux
```

После проверки запуска замерьте локальную модель на самом сервере:

```sh
python -m scripts.benchmark_local_llm_cuda --provider cuda --compare-cpu --warmups 1 --repeats 3 --output cuda-benchmark.json
```

Скорость научного энкодера E5 проверьте отдельно; команда сравнит батчи 8, 16
и 32 и покажет численные расхождения между ними:

```sh
python -m scripts.benchmark_e5_cuda --warmups 1 --repeats 3
```

Отчёт показывает время загрузки, обработки запроса и генерации, а также
проверяет формат ответа, точность цитат и различие между подходящим документом
и похожим по словам отвлекающим примером. Примеры синтетические: успешная
проверка не означает измеренной полноты поиска или точности всего анализа.
Сравнение с CPU позволяет увидеть расхождения ответов из-за вычислений на
другом устройстве; их следует разобрать на реальных запросах до постоянного
переноса анализа на сервер.
На текущей CPU-сборке модель проходит подходящий пример, но ошибочно принимает
отвлекающий документ, где вычисления выполняются электроникой. Бенчмарк
завершается с ошибкой качества, пока этот случай не исправлен и не проверен на
других областях. Само ускорение CUDA не устраняет эту ошибку отбора.

Проверка оборудования и замер полного анализа на будущем сервере ещё не
проводились. Приведённые ниже замеры — история разработки на другом наборе
данных и не являются обещанием времени на RTX 3070 или 4070.

## Скорость: что её съедало

Первый рабочий прогон дал 4 кандидата за 30 минут. Разбор по замерам:

1. **Кеш внимания ездил между видеокартой и памятью на каждом токене.** При
   4000 токенах контекста это 115 МБ за токен, и скорость падала с 45 до 10
   токенов в секунду. Кеш переведён на устройство через io binding: 38–57
   токенов в секунду независимо от длины контекста.
2. **Модель продолжала писать после закрытия JSON.** Генерация теперь
   останавливается ровно на закрывающей скобке первого объекта.
3. **Схема приходила как сгенерированный JSON Schema** — полтора килобайта
   вложенных определений. Малая модель читала это как шум и теряла ограничения:
   в одном замере повторяла фразу до упора в лимит токенов, хотя схема
   разрешала восемь. Теперь контракт передаётся списком полей в одну строку.
4. **Ответ начинался с пустого места**, и ближайшим образцом JSON-объекта для
   модели был сам входной материал — она его переписывала. Теперь ответ
   начинается уже внутри требуемого объекта (`{"candidates":`).
5. **Правила стояли перед материалом.** Малая модель сильнее слушает конец
   контекста: перенос полей и правил после материала оказался решающим — с
   29 до 5 секунд и с первой попытки вместо повтора.
6. **Партия именования уменьшена с 4 кандидатов до 2** для локальной модели:
   на четырёх она начинала пересказывать вход.

Итог на реальном материале: одна партия из двух кандидатов — **5,0 с** вместо
100 с, то есть примерно **2,5 минуты на 60 кандидатов** вместо часа.

## Замеренное поведение

На этой машине (CUDA, RTX):

* загрузка модели — 5,6 с, дальше она живёт весь прогон;
* скорость — 38–57 токенов в секунду, почти не зависит от длины контекста;
* именование двух групп документов настоящим промптом приложения — 5,0 с,
  258 токенов ответа, с первой попытки;
* описание области по запросу — 2,4 с, когда модель справляется.

Качество: именование работает надёжно — конкретная группа получает
`specific_technology`, обзорная группа про «энергохранение вообще» получает
`broad_topic`. Описание области малой модели даётся хуже: на пяти русских
запросах два ответа подряд не прошли проверку схемы (модель ставила
`technological: false`, заполняя при этом все остальные поля). Поэтому:

* один повтор с указанием отклонённых полей выполняется автоматически;
* если и он не помог, прогон **не падает**: область берётся из локального
  перевода запроса, ровно как в режиме без AI, и план записывает это
  происхождение (`local-translation-english-query/1.0.0`).

Сравнение квантизаций на задаче описания области: `model_q4` — 2 из 5 валидных
ответов и 24 с, `model_quantized` (int8, 1,58 ГБ) — 1 из 5 и 48 с. Поэтому
закреплён q4.

## Чем локальный клиент отличается от платного

[local_client.py](../../app/pilot/local_client.py) повторяет контракт
`generate_json`, поэтому вызывающий код, чекпойнты и ограничения не изменились.
Отличия только там, где они обязаны быть:

* **стоимость всегда ноль**, а вызовы и токены по-прежнему считаются в ledger;
* **разбор ответа терпимее**: модель оборачивает JSON в ```-ограждение или
  добавляет фразу — объект извлекается из текста, а не отвергается;
* **один повтор** при несоответствии схеме, с перечислением отклонённых полей;
  платному провайдеру повтор не даётся намеренно, там это стоило бы денег;
* **подсказка формата** (`local_hint`): пример заполнения для другой задачи.
  Платный клиент принимает этот аргумент и игнорирует — ему пример не нужен, а
  добавление изменило бы хеш промпта каждого платного запроса.

Инструкции, которые пришлось написать явно, перечислены в `PROMPT_SUFFIX`: не
печатать список допустимых значений вместо выбора, копировать идентификаторы
целиком, указывать то поле, откуда взята цитата. Каждая строка появилась после
того, как модель сделала обратное на настоящем промпте.

## Ограничения

* Модель общего назначения, а не предметный авторитет. Её предложение проходит
  те же проверки против документов, что и ответ платного провайдера.
* Прогон становится минутами вместо секунд: 60 кандидатов — это 30 вызовов
  именования по два кандидата, около двух с половиной минут, и это осознанная
  плата за отсутствие ключа.
* Отсутствующие веса обнаруживаются при старте анализа: клиент сообщает, что
  нужно выполнить `python -m scripts.install_local_llm` или нажать кнопку
  загрузки в настройках анализа.
