# Надёжный исторический сбор

Backend сохраняет план сбора по календарным годам или месяцам и выполняет отдельное
задание для каждого периода и источника. После остановки этот же план можно продолжить.
UI и ML не нужны. Существующая команда `collect` работает по-прежнему.

## Запуск

В PowerShell из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m app.backend --data-dir storage collect-history "neuromorphic computing" --from-date 2023-01-01 --until-date 2024-12-31 --period month --sources crossref openalex --limit-per-period 1000
```

Это первоначально 24 месяца × 2 источника = 48 заданий; лимит 1000 исходных записей применяется
к каждому заданию, включая невалидные записи. Для годовых периодов укажите `--period year`.
Границы включительные, без разрывов и пересечений; високосные годы учитываются.
Начальный и конечный периоды обрезаются по указанным датам. Если `--until-date`
не задана, дата сегодня UTC фиксируется при создании и не сдвигается при продолжении.

В новых планах включено автоматическое дробление: если успешная попытка достигла
лимита и источник не исчерпан, год делится на календарные месяцы, месяц — на дни.
Дочерние интервалы не перекрываются и в точности покрывают родительский интервал.
Частично выбранные годы/месяцы остаются обрезанными по датам запроса.
Источники разделяются независимо друг от друга.

Параметр `--max-periods 1200` ограничивает общее число узлов плана, включая родителей;
допустимо 1–10000. Начальных пар период/источник по-прежнему не более 1200.
Это ограничение одного плана, а не суммарного числа повторных попыток за его историю.
Для прежнего поведения добавьте `--no-auto-split` (в Python: `auto_split=False`).
Параметры сохраняются в плане и при resume не меняются.

Команда сразу выводит `history: <ID>` и далее прогресс в stderr. Итог — JSON в stdout.
Сохраните ID. Во время работы Ctrl+C отменяет сбор и дожидается завершения текущего
сетевого чтения. Для возобновления в том же каталоге данных:

```powershell
.\.venv\Scripts\python.exe -m app.backend --data-dir storage resume-history <ID>
```

Замените `<ID>` на напечатанный идентификатор. **Не создавайте новый `collect-history`,
если хотите продолжить прежний план:** эта команда всегда создаёт новое исследование.

Для просмотра после остановки/завершения, без интернета:

```powershell
.\.venv\Scripts\python.exe -m app.backend --data-dir storage histories
.\.venv\Scripts\python.exe -m app.backend --data-dir storage history <ID>
.\.venv\Scripts\python.exe -m app.backend --data-dir storage documents --history-id <ID> --limit 20
```

Один каталог данных по-прежнему имеет одного активного владельца Backend. Второй CLI-процесс
не открывает базу одновременно с первым. Во время сбора прогресс виден в его терминале;
интерфейс сможет опрашивать `get_history` у того же объекта Backend.

## Что означает полнота

### Читаемый отчёт и API прогресса

По завершении или после остановки откройте отчёт без сетевого запроса:

```powershell
.\.venv\Scripts\python.exe -m app.backend --data-dir storage history <ID> --format text
```

Для программного клиента доступен компактный JSON:

```powershell
.\.venv\Scripts\python.exe -m app.backend --data-dir storage history <ID> --format progress-json
```

Без `--format` остаётся прежний полный JSON HistoryReport — совместимость CLI сохранена.
В Python используйте `backend.get_history_progress(run_id)`. Он возвращает неизменяемую
модель `HistoryProgress` версии 1 из `app/backend/history_progress.py`, без исходных
метаданных документов, повторяющихся запросов заданий и сообщений исключений.
Вызов считывает согласованный снимок из базы, не ждёт окончания сбора и не обращается в сеть.
Второй процесс по-прежнему не может открыть каталог, занятый работающим Backend;
опрашивайте тот же объект из приложения, либо смотрите текущий вывод CLI.

Для каждого периода доступны: источник и даты, детализация, родитель, состояние,
полнота, текущий job-id, время изменения задания, число попыток, просмотренные,
сохранённые и пропущенные записи, объявленный источником размер выдачи и действующий
лимит. Для EPO учитывается предел 2000. Не начатые счётчики и неизвестный размер
выдачи возвращаются как null и отображаются знаком `?`, а не выдуманным нулём.
Успешная пустая выдача, напротив, имеет 0 записей и может быть полной.

`PeriodProgress.coverage`: complete — полная, incomplete — неполная/ошибка/остановка,
unknown — пока неизвестна (период ещё не закончен), replaced — полнота определяется
дочерними периодами. Причины неполноты отображаются по-русски, коды остаются в JSON.

`execution_percent` — доля обработанных конечных периодов (complete + partial + failed)
от текущего числа конечных периодов. **100% выполнения не означает полную выдачу:**
даже все задания с ошибками дают 100% выполнения и coverage_complete=false.
Отменённые/прерванные периоды не входят в обработанные. При дроблении знаменатель
растёт, а процент может уменьшиться. Процент собранного исторического корпуса и
оценка оставшегося времени не выдумываются. Счётчики документов разных периодов и
родительских выборок автоматически не складываются.

Во время `collect-history` и `resume-history` консоль выводит изменившиеся строки
периодов и общую сводку в stderr примерно раз в секунду. Неизменившиеся строки не
повторяются. Завершающий снимок выводится и для быстро завершившихся заданий, и
после Ctrl+C. stdout сохраняет прежний формат итогового JSON.

| Поле / состояние | Значение |
| --- | --- |
| `complete` у периода | Источник сообщил об исчерпании выдачи; нет пропусков и противоречия счётчиков |
| `partial` у периода | Загрузка успешна, но выдача ограничена, есть пропуски или противоречивый итог источника |
| `failed` | Попытка завершилась ошибкой; следующий период всё равно будет обработан |
| `pending` | Период ещё не запускался |
| `split` | Родитель заменён дочерними периодами; его попытка остаётся в истории |
| `parent_id`, `granularity` | Родитель и детализация конкретного узла: year, month или day |
| `total_periods` | Количество конечных периодов, без разделённых родителей |
| `total_plan_periods`, `split_periods` | Все узлы плана и число разделённых родителей |
| `cancelled` / `interrupted` | Отмена либо незавершённая попытка, обнаруженная после перезапуска |
| `processed_periods` | Количество периодов complete + partial + failed; это прогресс выполнения, не полнота корпуса |
| `coverage_complete` | Все периоды выбранного запроса complete и исследование успешно завершено |
| `full_calendar_period` | Интервал охватывает целый календарный месяц или год выбранной детализации |
| `partial_calendar_years` | Годы, охваченные запросом не целиком; важно даже при полном сборе отдельных месяцев |

У каждой попытки есть `scanned`, `stored`, `skipped`, `total_available` и ошибка.
`incomplete_reason` различает `source_not_exhausted`, `invalid_records_skipped`,
`inconsistent_total`, `daily_limit_reached` (лимит даже за день),
`period_budget_exceeded` (бюджета не хватает на всех детей сразу).
Общий статус `partial` не скрывает успешные задания других источников.
При дроблении знаменатель прогресса может увеличиваться. Родитель не считается
полностью собранным вместо своих детей: все конечные периоды должны стать complete.
CLI возвращает 0 только при полной выдаче выбранного запроса, 1 при неполноте/ошибке,
2 при неверных параметрах, 130 после Ctrl+C. Поэтому код 1 не обязательно означает
поломку программы: смотрите статус каждого периода.

Полнота относится только к поисковой выдаче источника, а не ко всем исследованиям
в мире и не к подтверждённым документам о тренде. Источники меняются между попытками;
это не единый транзакционный снимок внешних баз. Ограниченный текущий год нельзя
напрямую сравнивать с полным предыдущим. Даты записей имеют точность источника,
а тематическую релевантность должен проверять отдельный аналитический этап.

## Продолжение и ограничения

- `resume-history` пропускает complete и split; повторяет failed/cancelled/interrupted
  и выполняет ещё не начатые. Сохранённый переполненный partial-период при включённом
  auto_split дробится без повторного скачивания родителя. Остальные partial пропускаются.
- Чтобы также повторить partial-периоды, добавьте `--retry-incomplete`. Это не
  увеличивает лимит автоматически и не гарантирует, что ограниченный период станет полным.
- Дни больше не дробятся. При дневном лимите или нехватке бюджета остаётся partial;
  можно создать новый план с большим лимитом/бюджетом. Сетевые ошибки, невалидные
  записи и противоречивые счётчики сами по себе не запускают дробление.
- Возобновление выполняется **с начала незавершённого периода**, не с последнего
  сетевого курсора. Уже завершённые периоды не скачиваются заново. Это может повторно
  передать страницы незавершённого периода; документы дедуплицируются в общей базе.
- Каждая попытка — новый job с неизменяемым результатом. Поле `attempts` содержит
  все ID попыток периода. Старые страницы доступны через `documents --job-id <ID-попытки>`.
- `documents --history-id` использует последние попытки конечных периодов, включая их частичные
  результаты, и объединяет документы по внутреннему ключу. При повторе состав этой
  выдачи может измениться; для неизменяемого набора фиксируйте ID конкретных заданий.
  Сумма `stored` не равна числу уникальных документов нескольких источников.
- После дробления записи родительской выборки доступны в общей базе и через её job-id,
  но не добавляются к детям в выдаче исследования. Пока дети не собраны, документов
  исследования может стать меньше; это предотвращает смешение перекрывающихся выборок.
- Разница границ до 100 лет. Лимит периода —
  1–10000; EPO фактически ограничен 2000. Для EPO нужны ключи, живой доступ ещё не проверен.
- Один worker обслуживает обычные и исторические сборы. Длинный сбор занимает его
  до окончания/отмены. Очередь общая и ограниченная; 1200 периодов не создают 1200 futures.
- Между попытками пауза 1 секунда, настраиваемая в `BackendSettings.history_period_delay_seconds`.
  Межстраничные паузы, HTTP-таймауты и ограниченные повторы продолжают работать в адаптерах.
- После аварии запуск приложения не начинает сетевую загрузку сам: нужно вызвать resume.

## Python API для коллег

```python
from pathlib import Path
from app.backend.config import BackendSettings
from app.backend.history import HistoryRequest
from app.backend.service import Backend

with Backend(BackendSettings(data_dir=Path("storage"))) as backend:
    run_id = backend.submit_history(HistoryRequest(
        topic="neuromorphic computing",
        from_date="2023-01-01", until_date="2024-12-31",
        sources=("crossref", "openalex"), period="month",
        max_results_per_period=1000,
    ))
    progress = backend.get_history(run_id)  # Не ждёт окончания сетевого сбора
    report = backend.wait_history(run_id)  # Не вызывать в основном потоке UI
    documents = backend.list_documents(history_id=run_id, limit=100)
```

Также доступны `collect_history(request)`, `resume_history(id, retry_incomplete=False)`,
`cancel_history(id)`, `wait_history(id, timeout=None)`, `list_history(limit=50)`.
Timeout ожидания не отменяет работу. `cancel_history` возвращает принятие сигнала,
а не гарантию мгновенной остановки. Закрытие Backend отменяет и обычные, и исторические задания.
Контракты документов/заданий остаются версии 2. HistoryReport теперь версии 2:
добавлены дерево периодов и счётчики конечных периодов. Клиент должен учитывать состояние split.

## Хранение и проверка

Схема SQLite — 4: добавлены родитель, детализация и состояние дробления в history_periods.
Перед обновлением старой базы автоматически создаётся согласованная копия
`documents.sqlite3.before-v4-<id>.bak`. Старые документы, ревизии и задания не переписываются.
В старые планы явно записывается `auto_split=false`: их продолжение не должно неожиданно
увеличивать сетевую нагрузку. Для автоматического дробления создайте новый план.
Миграция выполняется при следующем открытии Backend; уже запущенный процесс нужно
штатно закрыть перед открытием новой версии. Основную базу при текущей проверке не меняли.
Создание попытки, задания и ссылки периода — одна транзакция; каждая страница сохраняется
отдельной транзакцией. Дочерние периоды и отметка split создаются одной транзакцией:
сбой не оставляет половину календарного разбиения. В базу не записываются ключи API.

Проверка: `python -m pytest -q`. Тесты включают завершение отдельного процесса через
`os._exit`, восстановление после запуска, отмену, изоляцию ошибок, повтор попыток,
сохранение старых снимков, транзакционный откат, миграции v1/v2, границы дат и CLI.

  2023–2024 годы, Crossref + OpenAlex, лимит 2 на период/источник. Четыре задания
  завершились успешно, сохранено 8 уникальных документов, пропущено 0.
